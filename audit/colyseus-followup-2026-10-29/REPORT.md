## Latest official stress attempt — 30 October

A fresh Industrial test targeted 63 Colyseus SDK clients plus one Web observer, for 64 human players. The test created its room in 585 ms, but the observer did not join within its 120-second gate. The harness stopped after 125 seconds. Only one SDK client joined; the room peaked at eight entities including seven server bots. No movement input, combat, grenade, or vehicle workload ran. This is an **incomplete test**, not a 64-player Web performance result. The raw result and resource samples are [saved here](sdk-web-64-incomplete.json) and [here](sdk-web-64-resources.csv).

The temporary helper was removed by its cleanup trap. A follow-up container check found no helper container; the candidate and legacy game containers were healthy. Candidate logs had no warning/error/exception lines in the preceding two hours. The private metrics endpoint returned 200; after cleanup it showed zero active rooms/players. Its recent-window tick p95 was 10.25 ms and p99 31.91 ms, while process event-loop delay p95 was 26.13 ms (maximum 237.11 ms). Those values came from an empty-room snapshot after the failed ramp and **cannot stand in for a full-room measurement**.

The best current full-room client measurement remains the earlier native cache-enabled run: 63 remote players, p50 frame time 16.67 ms, p95 28.88 ms, p99 55.21 ms, three disconnects and snapshot-gap p95 314 ms. That does not meet a 60 FPS budget or the reliability gate. The seven-bot native run stayed near 60 FPS, and the Web seven-bot run completed, but neither validates a full room. Full-room smoothness and Web reconnect behavior remain unverified; the Web full-room gate must be rerun with its observer present before the SDK cohort starts.

## Implemented and verified

- Reconnect timeout ends the SDK room and invalidates callbacks from prior sessions. Recovery waits for a newly decoded state containing the local player; the server-normalized identity is accepted. A deterministic lifecycle test passed, and two native two-peer tests against the candidate passed short reconnect, new input epoch, fresh state and removal. Web reconnect remains unverified; the pinned SDK documents automatic reconnection as native-only.
- The server consumes and acknowledges inputs while a player is dead, preventing those inputs from accumulating during the respawn delay. A real room test checks that this happens without moving the dead player.
- Repeated identical map updates no longer invalidate the client collision data. The client collision candidate cache was expanded from 12 to 64; shared fixtures and 150 additional sampled moves matched the reference across ten maps. The server cache was subsequently expanded from 12 to 32 and passed server geometry parity tests; live performance of that later server change must be measured separately.
- Full-client Web packaging checks both source fingerprint and hashes of the actual export. Explicit server-only packaging keeps the existing client version and marks the scope. A separate native export records the source, SDK and Godot versions and artifact hash. Provenance tests passed.
- Invalid map, mode and time values do not consume the shared room creation allowance. The remaining shared join ceiling is an overload limit; per-caller fairness is not established because the actual trusted proxy chain is unverified.
- Metrics use bounded timing samples and process-lifetime counters. The active candidate has a secret file and only serves metrics to its loopback interface with a valid bearer token; the public path returned HTTP 403. The process retained join/leave totals after rooms closed. A checker bug with plaintext 401 responses was fixed and the corrected checker passed inside the optimized candidate.
- Node StateView baseline, ownership filtering, reconnect and removal passed in an isolated reproduction. Native Godot peers saw only their own player entry even in its unfiltered baseline, so the Godot reproduction is inconclusive. Web StateView remains untested. StateView is disabled.

## Performance observations

These are bounded observations, not a production readiness claim. Both Mac runs used the exported build on Apple M4, Industrial, 1280×800, with actual candidate-server connections. The short run used a 120 FPS cap, one human and seven bots: p50 8.33 ms, p95 10.55 ms, p99 20.29 ms, max 141.66 ms; no disconnects, one death/respawn and car entry/exit observed.

The full-room run used a 60 FPS cap, one Mac observer and 63 SDK clients on Umbrel for a 60-second workload, with a 120-second observer window including ramp-up and cleanup. Its p50 was 16.67 ms, p95 50.03 ms, p99 69.23 ms; snapshot gap p95 was 366 ms. The observer disconnected once and reconnected. All 64 humans joined; helper data recorded 64 drops with one intentionally injected, 64 reconnects, ACK stalls in all 63 helper peers, and as many as 526 pending inputs. At a live 64-client sample, server tick p50 was 29.08 ms, p95 52.80 ms and p99 95.39 ms against a 16.67 ms target. Fire, movement, vehicle and removal events were observed, but confirmed hits and accepted grenades were not proven. These results fail the full-room performance gate.

Two in-app-browser attempts stalled downloading the game and logged a network error. A separate HTTPS download of the packaged game asset succeeded (29,552,203 transferred bytes in 33.5 seconds), but Web gameplay, frame times, reconnect and a full-room browser workload remain unverified. Reports: [native, seven bots](native-7-bots.json), [native, full room](native-64.json), [SDK full-room workload](sdk-64.json). Temporary helpers were removed; the candidate and main game containers remained healthy.

## Repeat with server collision cache optimization

The server-only image `warbase-colyseus:followup-geometry-20261029` (`a85b474e4364a94aab1356ba946d7fd6bcd401488fc412d5936295f2bc0d47f2`) reused the same client fingerprint and passed isolated startup and live private-metrics checks. A second 63-peer plus one Mac observer workload reached 64 humans. A sample while full showed server tick p50 17.93 ms, p95 42.42 ms, p99 59.27 ms. Sampling windows and gameplay differ, so the apparent improvement over the first run is not a controlled proof; the 16.67 ms target was still missed.

The repeat Mac observer recorded p50 16.69 ms, p95 50.41 ms, p99 98.49 ms and two disconnects. The helper reported stalls for all 63 peers and a maximum 720 pending inputs. Two confirmed hits were observed, but accepted grenade coverage was missing. See [repeat native report](native-64-after.json) and [repeat SDK report](sdk-64-after.json). Full-room smoothness and reliability remain failed.

Tunnel logs associated both browser failures with an unexpected EOF from the proxied game pack. The Go gateway's 30-second write deadline did not refresh for candidate assets. A scoped candidate asset-stream fix passed Go tests and an isolated gateway check, then was deployed in `warbase-server:colyseus-download-fix-20261029` (`4497d9678e40fb939490fa30bca970d88d5f6a2150e45eb5e55d3c98e57fc8db`), retaining the old gateway container for rollback. The next browser run finished loading the pack but could not load the Colyseus Web extension. A first attempt to preload the descriptor's nested path also failed; the browser explicitly requested the original SDK basename. The packager was corrected to preserve that basename and awaits browser verification.

The basename package was deployed in `warbase-colyseus:followup-web-basename-20261030` (`9426077846b2c35062481fa0edd6f90b8fae65bde9dc14fd505cff0af0761dd0`). It carries client source fingerprint `7906147970b645d74d73375871a0aa4cc537eaa2fb5b59452bcbc509cc1dc87d`, which adds QA-only pose timing to the earlier build. The in-app browser loaded the SDK and completed a 45-second match with one player and seven bots: p50 8.52 ms, p95 12.81 ms, p99 20.93 ms, one respawn, vehicle entry and driving, and no unexpected disconnects. The test ran in a background in-app browser; it did not establish fullscreen browser performance, Web reconnect behavior or 64-player Web performance. Previous candidate containers remain available for rollback.

## Client presentation profiling

An instrumented native export was run at the same 60 FPS cap in a seven-bot match and then in a 63-peer plus one observer match. These had different durations and actions and should not be treated as a controlled benchmark. In the seven-bot run, remote pose preparation had a p95 bucket upper bound of 0.5 ms and pose application 0.25 ms. In the full-room run, both had p95 upper bounds of 0.5 ms, with 63 peak remotes; their counters include ramp-up and cleanup. The full-room frame p95 was 38.33 ms and p99 130.58 ms; draw calls p95 were 899 versus 263 with seven bots. Recorded measurements do not establish the cause of those frame stalls, but do not justify changing state conversion or pose dictionary ownership solely to remove the measured preparation/application cost. [Seven-bot profiling](native-profile-7.json), [full-room profiling](native-profile-64.json), [full-room helper](sdk-64-profile.json).

An experimental bounded replay cache was then added to the client. It reuses a movement collision result only for exactly the same start, destination and loaded static map; it clears on map change and disconnect. The ten-map parity test and 150 varied moves matched the original solver. In a subsequent full-room native run it reported 21,363 hits and 29,001 misses, p95 frame time 28.88 ms and p99 55.21 ms, versus 38.33/130.58 ms in the prior instrumented run. Actions and network conditions varied, so the comparison suggests improvement but does not prove causality. Three disconnects and snapshot-gap p95 314 ms remain unacceptable. [Cache run](native-cache-64.json), [helper](sdk-64-cache.json).

The seven-bot cache run recorded 490 hits and 2,536 misses, p95 16.74 ms and p99 17.48 ms, with no disconnects. A client export ran concurrently during part of this run, so the timing is not a clean baseline. The cache-enabled native and Web builds share source fingerprint `48e5534ad6143f5484f34528fe3255349bf0e23a4a3f7d76628fda381308a1f0`; a two-peer native reconnect smoke passed. The cache-enabled Web build is deployed in candidate image `warbase-colyseus:followup-prediction-cache-20261030` (`47a01a49623a6e436c820366362b2c9971629c5a98536c0d32c524c3c9cc610e`). The prior candidate remains available for rollback. [Seven-bot cache run](native-cache-7.json).
